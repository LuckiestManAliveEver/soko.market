# Local schema scope

The current target is the React PWA. Its production driver is IndexedDB, already used by this repository. A typed, dependency-injected SQLite driver and executable SQLite migration are also supplied for a native host. `openSqliteLocalDatabase` accepts better-sqlite3's structural interface without bundling native binaries into Vite. Both drivers implement the same synchronous transaction callback and scope isolation. No Prisma schema exists here; Postgres uses `Cp2Snapshot` and the normalized CP2 tables.

| Mirror         | Cloud source                                | Reason                                                                                                                                                                                 |
| -------------- | ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| products       | cp2_products / ProductSummary               | Catalogue reads, create/update, stock count                                                                                                                                            |
| customers      | cp2_customers / CustomerSummary             | Customer reads and creation                                                                                                                                                            |
| invoices       | cp2_invoices / InvoiceSummary               | Read existing commercial records; confirm and payment require cloud                                                                                                                    |
| orders         | cp2_public_orders / PublicOrderSummary      | Merchant reads of existing storefront orders                                                                                                                                           |
| productFields  | cp2_product_field_schemas                   | Render the downloaded catalogue field layout                                                                                                                                           |
| receiptOcrJobs | cp2_receipt_ocr_jobs / ReceiptOCRJobSummary | On-device tesseract.js text extraction of a captured receipt (push-only: never pulled - supplier/sales-agent matching and confirmation still need the server's full contact directory) |

Store identity is in `runtime_scopes`, keyed by account, store and device. Local IDs and cloud IDs are distinct until acknowledgement. Every mirror row carries local_id, cloud_id, store_id, updated_at_local, synced_at and dirty. SQLite uses a composite scope/local_id primary key so two accounts cannot collide. Scope/store foreign keys, required fields, JSON validity and boolean checks are enforced. Initial schema migration is idempotent. The SQLite schema and generated SQL module must remain identical.

IndexedDB keeps the small pilot store as one structured record per scope, allowing transaction rollback and sequence allocation across tabs without an async transaction shim. SQLite maintains the same canonical state plus relational projections. This deliberately favors correctness for small stores; large catalogues need incremental row storage before broad rollout. Both drivers persist mutations and log entries together. The log contains the original mutation payload; identity mapping, acknowledgement and retry metadata can advance later.

Excluded: payment settlement, payment credentials, tax reporting, analytics, accounts/passwords/OTP/session credentials, memberships/role administration, logistics, supplier CSV imports, receipt-OCR confirmation/matching against the supplier directory, runtime training/evaluations, public checkout, arbitrary cloud tools and media blobs. These need live services, separate authorization, or larger storage. Receipt-OCR text extraction itself is the one exception - see receiptOcrJobs above. Stock movements are reconstructed as provisional UI responses from logged operations; authoritative movement IDs arrive through normal cloud processing. Cart is UI state, not a backend Prisma table. Conversation history remains in the existing account sync cache; peer transport uses the canonical message envelope without introducing a second message business model.

Runtime pins are device-local and excluded from all business pull application. There is intentionally no cloud pin table that could silently override a device choice. The new cloud migration adds receipt/change journals and a sequence watermark to the existing API service. It is generated only; it has not been applied to a shared environment.
